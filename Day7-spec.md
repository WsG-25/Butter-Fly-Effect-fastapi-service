## Project: Butterfly Effect - Garden Center Inventory API

## Overview

The goal of Day 4 is to build real CRUD operations for products by connecting FastAPI, Pydantic, SQLAlchemy, and PostgreSQL.

The API will allow garden center employees and managers to:

- Create new products
- View all products
- View a single product by ID
- Update existing products
- Delete products

This document defines the API contract before implementation.

---

# Product Model

A Product contains the following fields:

| Field | Type | Description |
|------|------|-------------|
| id | Integer | Unique identifier generated by database |
| name | String | Product name |
| unit | String | Measurement unit (each, bag, box, etc.) |
| cost_per_unit | Float | Purchase cost per unit |
| price_per_unit | Float | Selling price per unit |
| quantity_in_stock | Integer | Available inventory quantity |

# 1. Create Product

## Business Requirement

As a garden center manager, I want new products to be permanently saved so that product information remains available after restarting the server.

---

# Database Session Handling

The API uses a FastAPI dependency called:

```
get_db()
```

The dependency provides a database session for each request.

The route uses this session to communicate with PostgreSQL.

The session is automatically closed after the request completes.

---

# Response Model Decision

All endpoints that return product information use:

```
response_model
```

The reason is to control exactly what information is returned to API users.

The SQLAlchemy model represents the database structure, but the API should only expose fields that clients need.

Using response_model provides:

- A consistent API response format
- Protection from exposing internal database fields
- Easier future database changes
- Better separation between database and API layers

# Day 7: Modeling Relationships (Categories and Products)

## Overview

Until now, every database table has been independent. In a real application, data is connected through relationships.

On Day 7, a **one-to-many relationship** is introduced between **Category** and **Product**.

- One Category can contain many Products.
- Each Product belongs to exactly one Category.

The database enforces this relationship using a **foreign key**, ensuring that products cannot reference categories that do not exist.

API responses are also enhanced to return **nested data**, allowing clients to retrieve categories together with all associated products.

---

# Goals

- Create Category model
- Add foreign key relationship between Category and Product
- Create categories through the API
- Assign products to categories
- Return nested API responses
- Prevent invalid category references

---

# Pydantic Schemas

Separate schemas are used to provide different response formats.

## CategoryCreate

Used when creating a category.

```python
name
```

---

## CategoryResponse

Returned when retrieving a category.

Contains:

- id
- name

---

## ProductCreate

Contains:

- name
- unit
- cost_per_unit
- price_per_unit
- quantity_in_stock
- category_id

---

## ProductResponse

Returned when retrieving a product.

Contains:

- Product information
- Nested category information

Example

```json
{
    "id": 1,
    "name": "Sunflower Seeds",
    "category": {
        "id": 1,
        "name": "Seeds"
    }
}
```

---

## ProductInsideCategory

Used only inside the Category response.

Contains only product information.

Example

```json
{
    "id": 1,
    "name": "Sunflower Seeds",
    "unit": "bag",
    "price_per_unit": 6.00
}
```

Using separate schemas keeps API responses clean and prevents unnecessary or circular nested data.
